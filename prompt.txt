# Build Argon — CLI Argument Parser for Salam

می‌خوام یک کتابخانه‌ی کاربردی، تمیز و قابل انتشار برای زبان برنامه‌نویسی سلام (Salam) بسازی.

اسم پروژه `Argon` هست و وظیفه‌اش پردازش آرگومان‌های خط فرمان (CLI Argument Parser) است. این کتابخانه باید استفاده از آرگومان‌ها، فلگ‌ها، گزینه‌ها، دستورات و اعتبارسنجی ورودی‌ها رو در برنامه‌های Salam ساده و استاندارد کنه.

**مسیر دقیق پروژه:**

`/home/tikrack/Projects/argon`

## 1. قبل از شروع کدنویسی

ابتدا محیط و امکانات واقعی زبان Salam رو بررسی کن.

- مخزن اصلی زبان، مستندات، نمونه‌کدها و کتابخانه‌های استاندارد موجود رو بررسی کن.
- سینتکس واقعی زبان، نحوه‌ی تعریف تابع و ساختار، مدیریت رشته‌ها، آرایه‌ها، حافظه، فایل‌ها و دریافت آرگومان‌های خط فرمان رو شناسایی کن.
- اگر پروژه‌های قبلی Salam در سیستم موجود هستند، از ساختار و قراردادهای موفق آن‌ها الگوبرداری کن.
- بررسی کن آیا زبان امکان دریافت مستقیم آرگومان‌های CLI رو دارد یا به یک wrapper یا قابلیت دیگری نیاز است.
- API یا سینتکس خیالی نساز. هر قابلیتی که پیاده‌سازی می‌کنی باید با امکانات واقعی Salam سازگار باشد.

اگر قابلیتی مستقیماً قابل پیاده‌سازی نیست، بهترین راه‌حل عملی و سازگار با زبان را انتخاب کن و محدودیت آن را مستند کن.

بعد از بررسی، بدون متوقف‌شدن برای تأیید من، پیاده‌سازی را شروع کن.

## 2. هدف کتابخانه

Argon باید یک کتابخانه‌ی مستقل برای تعریف و پردازش رابط خط فرمان برنامه‌ها باشد.

برای مثال، API نهایی باید تا حد ممکن اجازه دهد برنامه‌نویس مفهومی مشابه این را پیاده‌سازی کند:

```text
argon = Parser("my-app")
argon.description("A sample Salam application")

argon.flag("verbose", "v", "Enable verbose output")
argon.option("output", "o", "Output file path")
argon.option("count", "c", "Number of items")

argon.command("build", "Build the project")

result = argon.parse(args)
```

این کد صرفاً نمونه‌ی مفهومی API است؛ آن را بدون بررسی سینتکس Salam کپی نکن. API نهایی را با زبان سازگار کن و در README نمونه‌ی واقعی و قابل اجرا ارائه بده.

## 3. قابلیت‌های ضروری

### A. آرگومان‌های موقعیتی

- دریافت آرگومان‌های موقعیتی مانند نام فایل یا مسیر.
- پشتیبانی از آرگومان‌های اجباری و اختیاری.
- پشتیبانی از چند آرگومان موقعیتی، در حد امکانات زبان.
- تشخیص تعداد آرگومان‌های نامعتبر.
- امکان تعریف توضیح برای هر آرگومان.

### B. فلگ‌ها

پشتیبانی از فلگ‌های بولی مانند:

```bash
my-app --verbose
my-app -v
```

قابلیت‌های مورد انتظار:

- نام بلند با `--`
- نام کوتاه با `-`
- مقدار پیش‌فرض `false`
- امکان تعریف مقدار پیش‌فرض برای فلگ‌ها، در صورت پشتیبانی API
- تشخیص فلگ ناشناخته
- پشتیبانی از فرم `--no-color` در صورت سازگاری با طراحی API
- پشتیبانی از فلگ‌های تکراری با رفتار مشخص و مستند

### C. گزینه‌های دارای مقدار

نمونه:

```bash
my-app --output build.txt
my-app --output=build.txt
my-app -o build.txt
```

قابلیت‌های مورد انتظار:

- مقدار رشته‌ای
- مقدار عدد صحیح
- مقدار اعشاری، در صورت پشتیبانی نوع‌ها
- مقدار بولی
- مقدار پیش‌فرض
- گزینه‌ی اجباری
- اعتبارسنجی مقدار
- تشخیص نبودن مقدار بعد از یک گزینه
- امکان محدودکردن مقادیر مجاز

### D. انواع ورودی

حداقل انواع زیر را تا جایی که Salam پشتیبانی می‌کند فراهم کن:

- String
- Integer
- Float
- Boolean

تبدیل نوع باید امن باشد. مقدار نامعتبر نباید بدون اعلام خطا به مقدار پیش‌فرض یا صفر تبدیل شود.

### E. دستورات فرعی (Subcommands)

مثال:

```bash
my-app build
my-app serve
my-app config
```

هر دستور باید بتواند توضیحات، آرگومان‌ها، فلگ‌ها و گزینه‌های مخصوص خودش را داشته باشد.

اگر پیاده‌سازی کامل دستورات تو‌در‌تو در نسخه‌ی اول پیچیده است، حداقل یک سطح subcommand را به‌صورت کامل و قابل استفاده پیاده‌سازی کن.

### F. Help و Usage

کتابخانه باید بتواند راهنمای استفاده را خودکار تولید کند:

```bash
my-app --help
my-app -h
my-app build --help
```

راهنما باید شامل این موارد باشد:

- نام برنامه
- توضیحات
- Usage
- آرگومان‌های موقعیتی
- گزینه‌ها و فلگ‌ها
- دستورات
- توضیح هر مورد
- مقدار پیش‌فرض در صورت وجود

خروجی باید خوانا، مرتب و مناسب ترمینال باشد. رنگ‌آمیزی اختیاری است و نباید باعث خراب‌شدن خروجی در محیط‌های فاقد پشتیبانی ANSI شود.

### G. اعتبارسنجی و مدیریت خطا

خطاهای زیر باید به‌صورت قابل فهم گزارش شوند:

- آرگومان ناشناخته
- گزینه‌ی بدون مقدار
- مقدار نامعتبر
- آرگومان اجباری مفقود
- مقدار خارج از محدوده
- دستور ناشناخته
- تکرار غیرمجاز یک گزینه
- استفاده‌ی نادرست از گزینه‌های کوتاه

پیام خطا باید تا حد امکان نام برنامه، گزینه‌ی مشکل‌دار و راهنمای اصلاح را نشان دهد.

کتابخانه نباید در مواجهه با ورودی نامعتبر به شکل ناخواسته crash کند.

### H. قابلیت‌های تکمیلی

در صورت سازگاری با امکانات زبان، این قابلیت‌ها را هم اضافه کن:

- حداقل و حداکثر مقدار عددی
- حداقل و حداکثر طول رشته
- انتخاب از فهرست مقادیر مجاز
- چند مقدار برای یک گزینه
- ترکیب فلگ‌های کوتاه مانند `-abc`
- جداکننده‌ی `--` برای پایان گزینه‌ها
- امکان غیرفعال‌کردن رنگ
- تکمیل خودکار دستورات برای Bash یا Zsh، در صورت امکان عملی

قابلیت‌های تکمیلی نباید باعث ناقص‌ماندن قابلیت‌های ضروری شوند.

## 4. طراحی API

API باید ساده، خوانا و قابل پیش‌بینی باشد.

- نام‌گذاری توابع و متغیرها انگلیسی باشد.
- از قراردادهای رایج CLI پیروی کن.
- رفتار هر گزینه در حالت‌های عادی و مرزی مشخص باشد.
- تعریف گزینه‌ها از پردازش آرگومان‌ها جدا باشد.
- parser بتواند چند بار برای برنامه‌های مختلف استفاده شود.
- در صورت امکان، ساخت چند parser مستقل در یک برنامه پشتیبانی شود.
- منطق parse، تولید help، اعتبارسنجی و مدیریت دستورات را بی‌دلیل در یک تابع بزرگ قرار نده.
- از وابستگی غیرضروری به کتابخانه‌های خارجی اجتناب کن.

**مهم:** هیچ APIای را صرفاً برای شبیه‌شدن به زبان‌های دیگر کپی نکن. طراحی نهایی باید با توانایی‌های واقعی Salam هماهنگ باشد.

## 7. مثال‌های قابل اجرا

داخل `examples/` چند برنامه‌ی واقعی بساز.

### مثال اول: Basic CLI

برنامه‌ای که نام کاربر را دریافت کند و با یک فلگ، خروجی متفاوتی ارائه بدهد.

### مثال دوم: File Converter

مسیر ورودی و خروجی را دریافت کند، فرمت یا حالت اجرا را اعتبارسنجی کند و تنظیمات را چاپ کند. لازم نیست تبدیل واقعی فایل را پیاده‌سازی کند؛ اما parser باید واقعاً کار کند.

### مثال سوم: Project CLI

دستورات زیر را ارائه کند:

```bash
project init
project build
project clean
```

هر دستور باید help و گزینه‌های مخصوص خودش را داشته باشد.

### مثال چهارم: Validation

مقدار عددی را دریافت کند و بازه‌ی مجاز را بررسی کند؛ ورودی نامعتبر باید پیام خطای واضح داشته باشد.

تمام مثال‌ها باید با سینتکس واقعی Salam نوشته شوند و تا حد امکان اجرا شوند.

## 12. Git و کامیت‌ها

داخل مسیر پروژه، مخزن Git را initialize کن.

تمام مراحل توسعه را در کامیت‌های کوچک و معنادار ثبت کن؛ برای مثال:

1. `chore: initialize project structure`
2. `feat: implement core argument parser`
3. `feat: add typed options and validation`
4. `feat: add help and subcommands`
5. `test: add parser test suite`
6. `docs: add README and examples`
7. `docs: build project documentation site`
8. `fix: resolve validation and edge cases`

این پیام‌ها صرفاً الگو هستند؛ پیام هر کامیت باید با تغییرات واقعی همان مرحله مطابقت داشته باشد.

- اگر مخزن از قبل وجود ندارد، آن را ایجاد کن.
- اگر مخزن موجود است، تاریخچه یا تغییرات قبلی را بدون دلیل حذف نکن.
- فایل‌های نامرتبط را وارد کامیت نکن.
- از force push استفاده نکن.
- نیازی به ساخت مخزن remote یا انتشار آنلاین نیست، مگر اینکه ابزار و دسترسی لازم وجود داشته باشد.
